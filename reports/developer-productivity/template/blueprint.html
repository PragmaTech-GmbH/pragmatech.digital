The Spring Boot Testing Skills Blueprint

How I structure my agentic skills for Spring Boot testing in Claude Code, GitHub Copilot, Cursor and Codex.

What is a skill?

A skill is a folder with a SKILL.md file and supporting Markdown files that your coding agent loads when a task matches. It adds more determinism to agentic coding: the agent follows your team's written decisions instead of making a new guess in every session.

This blueprint shows the structure, not a finished skill. Use it to put your own company and industry best practices into skills that your whole team can read, review and improve. The output of an agent still varies, so keep reviewing it.

Sample skill: integration-testing - Part 2

The anatomy of the skill

On the left is the outline of my SKILL.md, on the right what each part is for. The description is a new example for this blueprint.

--- name: integration-testing description: <what it does>. Use when <your trigger words>. Not for <neighbor skill's job>. ---
The trigger. The agent reads name and description to decide whether to load the skill. Say what it does, when to use it, and what belongs to another skill.
# <Title> + short intro
The goal. Define the test type in your words and name the goals that every later rule serves.
## Adapt this template
Your base decisions from page 2, in one table.
## Scope
The right tool? Tell the agent when a cheaper test type is the better answer.
## Non-negotiables
The short list that holds for every test. Detail and reasons stay in the references.
## Workflow: write a test
Ordered steps. Start with "find the base class" and end with a check that the agent runs itself.
## Journey anatomy
One complete example from your domain. Agents copy examples closely, so make it your best test.
## External systems, infrastructure, config ## Fast integration tests ## Parallel and independent
The hard topics. This is where your project knowledge goes: what the application needs to start, what makes the suite slow, and what each test must own.
## Workflow: review tests
The second use. The same standards check existing tests and report findings in a fixed format.
## Reference files
The index. Each file with one line on what it holds, so the agent knows what to open.
integration-testing/ ├── SKILL.md └── references/ ├── testing-standards.md ├── examples.md ├── project-setup.md ├── base-class.md └── external-systems.md

testing-standards.md
Your coding best practices. Each rule has an ID, a severity, the reason and what it means in Java, so findings can point to it.
examples.md
Good and bad pairs for the rules that need code to be clear.
project-setup.md
The project configuration that the rules depend on: build, dependencies, logging, CI.

external-systems.md

Layering
The agent sees the description first, then loads SKILL.md, then opens a reference file only when it needs it. Essentials go up, detail goes down.

Repeat the pattern

One pattern, seven testing skills

I repeat this anatomy for the other testing aspects. For a typical Spring Boot project, this is the set of skills that I usually go with. A small router sits in front, holds the decisions that all skills share and sends each task to the right skill.

spring-boot-testing (router)Shared project decisions - picks the right skill for the task
unit-testingBusiness logic without a Spring context.
slice-testingPersistence, JSON, HTTP clients and listeners.
slice-web-testingThe web layer, including security.
integration-testingUser journeys against the running application. The sample on pages 2 and 3.
testcontainers-setupThe shared container infrastructure that other skills build on.
e2e-ui-testingBrowser journeys through the user interface.
test-setup-reviewA read-only review of a single test or a whole suite.
How fine should you cut? One skill per job with its own trigger. Each topic has exactly one owner. Split when two jobs need different decisions, merge when you cannot say which one applies.

What I encode, so the test suite stays fast

Test data setupMy integration-testing skill knows how to set up data so that each test owns it. That is the entry ticket for running integration tests in parallel.
ParallelizationThe skills know what must not be shared between tests, and how to prove that a test is safe to run next to others.
Spring context reuseEvery additional application context costs start-up time. The skill treats a new one as a decision, not as an accident.
End-to-end structureThe e2e-ui-testing skill knows how to structure a proper browser journey, so UI tests stay readable and stable.
The effect adds up: tests that the agent writes already follow the practices that keep your build fast. How much time you gain depends on your suite, so measure it before and after.

Your turn

Build and share your own skills

  1. Define the granularity. List the test types your project really uses. Start with the one that hurts most.
  2. Collect your best practices. Take them from your best tests, recurring review comments, team guidelines and past flaky tests. Add the industry practices you agree with.
  3. Write the skill. Base decisions and essentials go into SKILL.md, the detail into references/.
  4. Install it where your tool looks for skills, and mention it in your agent instruction file.
  5. Check and improve. Give the agent a real task. When it guesses or gets it wrong, fix the skill, not only the test.
Project skills - my usual defaultHow a team tests depends on the team and the project. Check the skills into the repository. They are plain Markdown files: you review them in pull requests, and every teammate gets them with the next pull.
Global skillsFor personal habits and general practices that you want in every project. They stay on your machine, so your team does not get them automatically.
